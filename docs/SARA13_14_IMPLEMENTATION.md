# SARA 13/14 — scoped research, learning and creative workspace

Status: **incremental implementation, not a release certification**. This checkout is React/Vite/Electron/Capacitor (not Expo). Older chat/voice/task/visual/Windows modules were retained. `LEARN` and `CREATE` open lazy-loaded owner-only panels in the legacy desktop workspace; neither exposes provider credentials to the renderer. They deliberately **deny every route in protected multi-user mode**, including the owner, until a separately reviewed per-user migration is built. Neither panel is a replacement for the existing Windows Office and visual workflows.

## New: evidence-backed project workflow

Open **PROJECTS → choose an existing active project → Evidence & approvals**, and unlock with the local owner approval token. An existing Gemini key or configured text provider is still required by the overall first-run frontend gate; the board itself never contacts a model. This ledger lives under the private `SARA_DATA_DIR/research/project-evidence.json` and remains **disabled in protected multi-user mode**. Its UI is lazy-loaded and clears the token on close.

1. In **LEARN**, explicitly retrieve permitted HTTPS source URLs. On the project board, link only actual *completed* research job/source IDs. Links store retrieval time, URL and SHA-256; source passages are **untrusted data**, not instructions or approved facts. Optionally link human-reviewed knowledge with matching source hashes. Deleted/revised, future-dated or >30-day-old source evidence blocks acceptance.
2. Write a human-authored brief, then explicitly review its exact digest. This is a **human-reviewed brief, not independent factual verification**. A change to sources, reviewed knowledge, the existing project's title/description/due date, or the brief invalidates earlier review. A renamed project must be deliberately rebound and reviewed again: the owner sees the **latest server-returned title, description, status and due date**, and the rebind endpoint compares their exact fingerprint with the current project before clearing both approvals. If details change while the owner is reviewing, the rebind is refused and a fresh view is required.
3. Open **CREATE** through its separate provider/budget/consent flow or use the offline tone/mesh alternatives. Link a Studio job if its process-local status is available and link an actual saved file; the board independently rechecks its on-disk SHA-256 and size in bounded memory (format was validated when Studio saved it; the report does not re-parse the media). Jobs interrupted by a restart are marked unknown, never fabricated as completed; the owner can unlink an unrecoverable job and re-evaluate the intact artifact. A local export without a job may still be linked with explicit review. Revision links preserve original files. Canceling the **board** does not cancel a separate job or delete anything; cancel a selected linked job separately, then poll its status.
4. Review every linked file and limitation before marking the exact manifest **HUMAN_ACCEPTED** for **manual use only**. No autonomous model action, deployment, publication, native Office test or skill promotion results. Tampering/deleting a linked file or changing its evidence returns the board to **STALE**. Owner-only JSON manifest download contains links, digests, estimated costs and warnings but no original media bytes; check that the browser actually saved it. The local activity list is bounded and **not tamper-proof**. This is a single-backend ledger, not distributed coordination.
5. `GET /api/owner/release-readiness` shows *counts only* from a local Git checkout, with no paths or contents and no deletion. `BLOCKED` remains until the owner reviews credentials/history and performs agreed non-destructive deindexing. A clean index would still require history and platform review; in packaged installs without `.git` the status is `UNAVAILABLE`, **not pass**.

Artifacts are new private files under `SARA_DATA_DIR/studio/` (or the existing default private data root) with hash, format, dimension/duration/topology and size checks. History records original and revision IDs. Successful status requires a verified disk write; failed/cancelled jobs never claim a saved artifact. MP4 rendering and text/media calls use an asynchronous one-at-a-time studio queue, while chat remains responsive. The HTTP test holds one generation open, verifies chat responds, cancels it, and confirms protected-mode activation does not save pending output. The new UI uses a local owner token kept only in React memory; closing/unmounting the panels clears it. On a 401/403 it drops owner-only lists, brief and manifest data and rejects delayed responses from an older session. Failed checks label the displayed checkpoint **last-known only** and disable review/acceptance until a fresh check succeeds; server-side authorization and revision checks are still authoritative. Server stores remain private and use restrictive file permissions where supported (Windows ACLs need separate review).

## Private configuration (never commit secrets)

1. Use Node 22 and existing project setup (`npm ci`). Start from an ignored local `.env` or a private process environment. Set an installation-specific `SARA_ADMIN_TOKEN` (at least 32 characters) and optional absolute private `SARA_DATA_DIR`. The existing first-run frontend gate also requires either a configured Gemini key or a configured text-model provider before opening the overall workspace, even for the offline Studio controls. `src/App.tsx` is a desktop owner workspace; `/api/users/bootstrap` switches to protected multi-user mode and intentionally locks these unported owner-only routes.
2. Configure exactly the provider roles needed: `SARA_TEXT_PROVIDER`, `SARA_TEXT_MODEL`, and optional `SARA_CREATION_PROVIDER`/`MODEL`, `SARA_CODING_PROVIDER`/`MODEL`, or `SARA_RESEARCH_PROVIDER`/`MODEL`. Official OpenAI uses `OPENAI_API_KEY`; Anthropic uses `ANTHROPIC_API_KEY`; Gemini uses `GEMINI_API_KEY` or existing key onboarding. An OpenAI-compatible endpoint uses the separate `SARA_TEXT_API_BASE_URL`/`SARA_TEXT_API_KEY`; only HTTPS or a trusted local loopback endpoint is accepted. A ChatGPT subscription/site login is **not** API access. Provider names and model entitlements must be verified against your own API account.
3. If limiting estimated text USD cost, set `SARA_TEXT_MAX_ESTIMATED_USD` **and** per-million input/output prices for every selected provider (see `.env.example`); missing price fails closed. Text token/session budgets are process-local, not invoices. Media requires an explicit `SARA_STUDIO_DAILY_ESTIMATED_USD` and per-request prices. This media-attempt ledger persists across restarts; estimates remain approximate and failures may bill.
4. PNG generation: set `SARA_IMAGE_PROVIDER=gemini` or `openai`, `SARA_IMAGE_MODEL`, matching API key and `SARA_IMAGE_ESTIMATED_COST_USD`. Image edit separately requires `SARA_IMAGE_EDIT_PROVIDER=openai`, `SARA_IMAGE_EDIT_MODEL`, `SARA_IMAGE_EDIT_ESTIMATED_COST_USD`, API key and reference consent. TTS requires `SARA_AUDIO_PROVIDER=openai`, `SARA_AUDIO_MODEL`, `SARA_AUDIO_ESTIMATED_COST_USD_PER_1K_CHARS` and API key. No defaults imply that a model is available.
5. MP4 montage: set `SARA_FFMPEG_PATH` to an **absolute owner-reviewed** local executable with libx264. Do not point it at a user-uploaded script. Native Windows codec, Office COM, capture, UIA, Android and biometrics must be tested on their platforms.
6. Only after an independent Docker/host threat-model review, set `SARA_ENABLE_DOCKER_SANDBOX=true` and a locally cached, digest-pinned `SARA_SANDBOX_IMAGE=name@sha256:<64 hex>`. Do not pass provider secrets into the image. Do not run untrusted code on an unreviewed shared host. The absence of Docker keeps all tests unavailable, not magically passing.
