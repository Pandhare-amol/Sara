# SARA agent engineering report (2026-10-15)

## Phase 0 — repository audit and baseline (before implementation)

**Actual application, not the proposed template:** React 19 + TypeScript 5.8 + Vite 6 web UI (`src/main.tsx` → `src/App.tsx`, with `App.tsx` as an older second UI), packaged with Electron (`electron/main.cjs`) and Capacitor Android. `app.json` contains Expo metadata, but there is no Expo dependency or Expo start/build script. Do not move the app to Expo. Voice uses `src/lib/audio.ts` → `/live` WebSocket → Gemini Live in `server_full.ts`; text uses `/api/chat`. The Node/Express backend entry point is `server_full.ts` (`server.ts` is a second, older server); `mobile_server.ts` is a separate mobile text endpoint. Python 3/FastAPI `desktop_agent/main.py` on loopback owns Playwright and native desktop tools. `server_task_manager.ts`, `src/core/automation`, `src/core/tasks`, `src/services/ClosedLoopExecutor.ts`, `server_memory.ts` and `src/services/Memory*` are partially overlapping task/memory layers. The closed-loop executor currently **refuses** desktop actions because planning/execution/verification are not connected; do not mistake its passing guard tests for desktop capability.

**Existing security boundary:** Node binds to loopback by default; remote bind requires TLS and a bearer token. The `/api` middleware checks Host/Origin and remote identity. The desktop agent binds to loopback by default; remote bind requires TLS and a token. Local desktop-agent endpoints and UI API routes still assume trusted local processes. Existing tool permission metadata and confirmations have inconsistencies; work on these only behind the existing server/tool boundary. Runtime state lives in `data/`, although many historic runtime files were already committed; those need separate credential rotation and Git history remediation.

**Dependency/report:** npm dependencies are locked in `package-lock.json` (`@google/genai` 2.x, Express 4.x, `sql.js` 1.x, Playwright dev dependency); Python agent dependencies are pinned in `desktop_agent/requirements.txt` (FastAPI, Playwright 1.49.1, PyAutoGUI, Windows-only pywin32). No dependency upgrades are required for the initial implementation. This Linux sandbox has Node 22, npm 10, Python 3.11; no installed Python desktop dependencies, GUI, Windows UI Automation, browser executable, or Gemini key. `npm ci --ignore-scripts --no-audit --no-fund --prefer-offline` installed the *locked* JS dependencies for baseline checks (no manifest changes).

**Measured baseline:** `npm run lint` PASS; `npm run build` PASS (Vite warns about a >500 kB chunk). `test:agi` 19/19 PASS; `test:api` 8/8 PASS; `test:voice` 10/10 PASS; `test:closed-loop` 9/9 PASS; `test:autonomous` 4 PASS, 4 SKIPPED (requires real desktop); `test:persistence` 19/19 PASS. `test:security` 24 PASS, 1 FAIL: `tests/security/tracked-runtime-data.test.ts` detects ~1,200 *pre-existing* tracked generated/private files. No secret content was printed. Removing these from current HEAD without rotating/revoking credentials and assessing published history is not sufficient; avoid modifying tracked user data in a feature patch.

## Phased implementation plan

1. **Preserve and stabilize:** Keep existing UI, voice, desktop bridge, memory and build intact. Repair only proven permission bypasses. Use the current Git branch for rollback, do not migrate data destructively.
2. **Text model abstraction:** Add a bounded provider/role adapter using the existing Gemini SDK and an optional OpenAI-compatible endpoint, connect it to both `/api/chat` implementations, expose key-free status, and keep Gemini Live voice independent. Test against an in-process fake HTTP provider; live model availability must be verified on an actual installation.
3. **Bounded workflow:** Compose the existing task store and desktop tool gateway instead of granting a model a new shell. Validate model-proposed JSON plans against a tiny allowlist, show the plan, execute sequentially with deadlines, verify before advancing, pause for an explicit, targeted approval if necessary, and support pause/resume/cancel. Uncertain side effects are never auto-replayed.
4. **Browser verification / memory:** Harden the already-present Playwright tools for actual DOM/URL postconditions and no implicit form submission. Reuse existing memory APIs for explicitly approved context; do not claim the separate memory stores are consolidated. Run unit/local fixture tests where dependencies are available.
5. **Release and gaps:** Re-run lint/build/regressions/security and document expected vs actual safe scenarios. Windows UI Automation, reliable remote cancellation, full credential/history cleanup, cross-platform live browser/voice/model tests, code-writing autonomy, benchmarked learning, and AGI/ASI are later work, not claims of completion.

The code changes and scenario-by-scenario verification results are appended below after implementation.

## Implementation result — bounded agent path, not an AGI release

This phase extends the existing UI/server instead of replacing it. The actual path is:

```text
Vite src/App.tsx (TASKS) -> TaskManagerPanel.tsx -> same-origin /api/workflows/browser/*
                               |                    -> /api/memories/* (Memory dashboard)
Express server_full.ts -> TextModelRouter (chat/planning, backend keys only)
                       -> BrowserWorkflowEngine -> persisted task/checkpoint
                       -> ToolRouter + deterministic policy -> Python desktop agent
                       -> isolated, sandbox-required Playwright browser context
```

- **Text:** `src/core/models/textModelRouter.ts` routes bounded chat/planning requests to the existing Gemini SDK or a server-configured OpenAI-compatible endpoint. It enforces timeouts, limited retry, maximum output and an in-process output-token reservation budget; missing providers fail closed. Desktop and mobile chat call it; Gemini Live voice remains separate and unchanged. Coding is a reserved role, *not* an enabled coding agent (`executionEnabled: false` in model status). A configured model name is not proof the provider supports it.
- **Task planning:** `POST /api/workflows/browser/plan` requests short JSON from the planning model, rejects unknown fields/actions, and saves a paused task with a SHA-256 plan digest. A human can review the entire plan in **TASKS**. `start` may run only the reviewed navigation/read portion. At most five steps, two fill/click steps, one public HTTPS hostname, and a 90-second workflow budget. `fill` and `click` require an authenticated, explicit approval for the *current* step/digest; approvals expire after 60 seconds and are consumed before dispatch. A concurrent duplicate approval is refused. The model, page text, and client-supplied confirmation flags cannot grant approval. Generic task mutation/retry excludes workflow tasks.
- **Actual browser bridge:** `desktop_agent/tools_browser_workflow.py` drives a real Playwright browser **when installed**. It uses accessibility roles/labels with exact names, an ephemeral nonpersistent context, a Chromium sandbox requirement, disabled downloads/service workers/WebSockets, same-host request routing and public-address DNS checks. It blocks login, payments, submissions, deletes, sends, publishing and similar high-impact controls: DOM text is not proof of a real external transaction. It separately inspects the expected URL, visible text or field value after the action. A navigation/click is not reported verified merely because it was dispatched. DNS rechecking is *not* a complete defense against DNS rebinding.
- **Observed vs predicted:** checkpoint `expectedPostcondition` is the plan's expectation; `completed[].evidence` and `observedAt` are recorded observations. The UI labels these separately. Missing verification ends in `partial`; an interrupted/in-flight action becomes uncertain and cannot be silently replayed. Pause/cancel is cooperative during an in-flight desktop call, not immediate preemption. This is a narrow verified *browser-page* outcome, not independent proof that a remote system committed a write.
- **Memory:** `server_memory.ts`, `src/core/memory/approvedMemory.ts`, `src/services/MemoryRepository.ts` and the dashboard store explicit user-provided memories with provenance/approval/expiry, edit and deletion; legacy or inferred rows remain visible for review but are excluded from agent retrieval and truth context. Retrieval is bounded lexical matching, not an embedding quality claim. Voice commands only accept an explicit small grammar (`remember my ...`, `forget my ...`). Automatic inference is opt-in (`SARA_AUTO_MEMORY=true`) and still produces *unapproved* rows. Legacy `/api/cognitive/remember`, `/api/cognitive/memory/consolidate`, and `/api/cognitive/task/execute` now return 410 rather than bypassing these boundaries; other cognitive read/plan routes remain. Separate older Python/cognitive memory subsystems are not consolidated.
- **Local evaluation / review:** `scripts/evaluate-agent.ts` executes version-controlled deterministic fixtures from distinct development and local-holdout files and reports observed pass/fail, split/category counts, measured fixture latency, Wilson uncertainty and unmeasured capabilities. `scripts/review-agent-evaluation.ts` validates two local report files, rejects missing/reclassified/regressed/failing cases and inconsistent counts, and otherwise says only `human_review_required`. It writes an ignored local report. It does not write code, run proposed code, sandbox a patch, deploy, or attest provenance of externally edited reports.

### Installation and configuration

1. Use the repo's existing supported Node/Python installations. `npm ci` uses the lockfile; no major dependency was upgraded. For the desktop agent, install `python -m pip install -r desktop_agent/requirements.txt` and `python -m playwright install chromium` **on an appropriately configured target machine**. The Chromium process sandbox must work; the workflow fails closed otherwise. The sandbox/browser was not available here. For an existing SARA install, keep its current desktop-agent deployment and port; do not expose the Python agent to untrusted processes.
2. Keep `.env` private. Supply `GEMINI_API_KEY` or the app's existing key onboarding for Gemini; alternatively set `SARA_TEXT_PROVIDER=openai-compatible`, a supported `SARA_TEXT_MODEL`, `SARA_TEXT_API_BASE_URL` (HTTPS or loopback HTTP), and `SARA_TEXT_API_KEY` if required. The default model identifier must be checked against the user's actual provider account before use. Never put server keys in a `VITE_` variable or commit them.

Loopback alone does **not** authorize approval. Node and Python bind to loopback by default. Data location may be changed with `SARA_DATA_DIR` (keep it private/backed up).
4. Run the existing app with `npm run dev` (Express serves the Vite UI and same-origin API together on localhost:3000), or use the repo's Electron/production commands. A separate `npm run dev:ui` server needs the existing `SARA_UI_API_PROXY_TARGET`/`SARA_PREVIEW_HOST` proxy configuration before its `/api` calls will work. In the app select **TASKS**, propose a public starting URL and goal, inspect the plan, start, and authenticate/approve each fill/click. **Memory** offers explicit create/edit/delete. If Python dependencies, sandbox support, a model, or an admin credential are absent, these features display errors instead of pretending to act. Voice still needs its existing Gemini Live configuration. For offline checks: `npm run test:agent-core`, `python -m unittest tests/test_browser_workflow.py`, `npm run eval:agent`, and `npm run review:agent-eval -- <baseline.json> <candidate.json>`.

### Security review, blockers, and Version 2.0 roadmap

- **Stop-ship:** Many historical runtime/generated/private paths are already Git-tracked despite `.gitignore`. Audit the tracked set and published Git history privately, revoke/rotate any exposed credentials, remove sensitive content from tracking and (with owner coordination) history, then rerun `test:security`. Deleting a few current working-tree files or reporting 24 passes does **not** fix past exposure. Avoid a broad destructive cleanup in this feature patch.
- **Remaining risks:** A compromised local process can call the loopback desktop agent directly; browser DNS rebinding/TOCTOU and browser-level egress beyond intercepted HTTP/WebSockets need a network-enforced egress allowlist for higher-assurance sites. A site can present misleading confirmation text; high-impact actions are forbidden until purpose-built, independently verified integrations exist. Cancel cannot undo in-flight effects. Admin approval currently authorizes only the displayed step/digest, not arbitrary trusted execution. Historical/older Python and cognitive automation/memory, UI and voice tool paths remain separate systems and require a comprehensive permission audit before claiming one central policy for every tool. In-process token budgets reset on restart; they do not measure billing or cap concurrent provider charges globally. Existing `test:security` failure blocks any production security claim.
- **Phase 2 (operational hardening):** resolve tracked-data/history incident, add strict authenticated access to every local desktop entry point, deploy behind process/network isolation and pinned egress, test real Playwright on target platforms with sandbox enabled, run Windows/Android packaging and authenticated admin UX tests, add robust abort/status reconciliation and independently verified high-impact adapters, measure errors/cost/latency. Keep voice and legacy features functioning while migrating individual tools to the central gate.
- **Phase 3 (experimental agents):** only after the above, add narrow permission-limited specialist agents with explicit task handoff, provenance/versioned *reviewed* skills with prerequisite checks, and observation freshness requirements; evaluate each addition against a real baseline. Do not infer a skill's success merely from a page postcondition or replay across sites without fresh review.
- **Phase 4 (research, not shipped):** build a genuinely isolated, disposable, network/permission-limited coding laboratory that proposes a diff, tests it against independently maintained hidden cases, measures resource use/regressions, and *requires human code/security review* before applying anything. Develop counterfactual outcome tracking that distinguishes predictions from observed outcomes. Randomize new held-out scenarios and run live-provider/real-desktop experiments with explicit cost and failure accounting. Current CLI report comparison is **not** that lab. Reproducible continual learning, multi-agent gains, AGI and ASI are hypotheses, not demonstrated capabilities.

Recommended next experiments: compare no-memory vs approved-memory chat answers on consented tasks; compare a single planner vs narrow specialists on the **same unseen scenarios**, reporting cost, confidence intervals and failures; measure DOM postcondition reliability against independent server-side test oracles; run prompt-injection and redirect/DNS-rebinding adversarial pages in a dedicated test network; and report both positive and negative results. Keep the held-out cases out of tuning, and do not use the checked-in local-holdout fixtures as evidence of generalization.

## SARA 3.0 reliability increment — cancellation linearization (2026-10-15)

### Re-audit and scope decision

The current UI entry point is `src/main.tsx` → `src/App.tsx` (React/TypeScript/Vite); Electron wraps it and Capacitor provides Android packaging. `app.json` has Expo metadata, **not** an Expo dependency/start script. The active API is `server_full.ts` (Express); `mobile_server.ts` is a separate mobile text endpoint; `desktop_agent/main.py` dispatches local Python tools, with a separate Playwright workflow module. The `/api` host/origin/remote-token guard, admin approval, `ToolRouter`, and workflow engine are independent layers. There are still older `server.ts`, cognitive, Python-agent, and memory paths; none is being replaced by a fabricated Expo or fully centralized agent. Voice, chat and the companion UI were left intact. No dependencies were added or upgraded in this increment.

**Before editing:** lint and `test:agent-core` (20/20) passed. `test:security` passed 24/25; its tracked-runtime-data check finds **1,205** pre-existing generated/private tracked paths. This is a release blocker requiring owner-led credential rotation/history review and careful Git cleanup, *not* a reason to erase local user data. No live Python FastAPI/Playwright/PyAutoGUI installation, Windows desktop, or browser binary was available here.

**File-level defect and plan:** `BrowserWorkflowEngine.start()` could await a paused task snapshot while `stop()` cancelled the task. The old `start()` would later proceed from the stale snapshot; the drive could dispatch browser operations from a cancelled task. Another race allowed `stop()` between writing the in-flight marker and invoking the desktop tool, yet the tool still ran. Two deterministic tests failed on the old code. The bounded plan was to (1) serialize same-task start/approve/stop transitions without holding a lock during Playwright I/O, (2) register stop intent synchronously and check it before dispatch, (3) retain safe checkpoints and keep uncertain in-flight effects uncertain, and (4) rerun broader regressions. This phase is complete; later phases below remain open.

**Changed in this increment:** `src/core/workflows/browserWorkflow.ts` serializes same-task UI transitions, keeps cancel above pause when they race, refuses stale starts/approvals, and checks stop intent again after persisting the in-flight marker. A stop before dispatch clears that marker; a stop during an action is cooperative, verifies what can be verified, and prevents the next step. If the action fails after dispatch, the outcome stays `partial`/uncertain rather than being mislabeled cancelled. When all plan steps have already been independently verified, a stop during the terminal commit is **rejected**, not falsely acknowledged. While a call is pending, `get()` shows process-local `stopRequested` in the UI; the final checkpoint is persisted after the call settles. A process crash in that interval is handled by existing uncertain-action recovery; this is not a guarantee of immediate OS-level cancellation or of coordination across multiple server processes. `tests/browser-workflow.test.ts` covers the controlled races, priority, pause/resume and uncertain outcomes; `tests/api/browser-workflow-http.test.ts` covers cancel/restart over HTTP.

**Actual post-change checks:** `npm run build` PASS (includes lint; pre-existing Vite chunk-size warning); `npm run test:agent-core` **28/28 PASS**, including the new race tests; `npm run test:api` **9/9 PASS**; `test:voice` **10/10**, `test:closed-loop` **9/9**, `test:persistence` **19/19**, `test:agi` **19/19**, `test:autonomous` **4 PASS / 4 intentional real-desktop SKIP**. Python fake-page/context workflow tests **5/5 PASS**. `npm run eval:agent` still reports **13/13** deterministic fixtures (development 5, local holdout 8; Wilson 95% interval 0.772–1.000). These fixture counts do not measure live-model, Windows, or real-browser success. `npm run test:security` is still **24 PASS / 1 FAIL** on historical tracked runtime files; therefore the requested 100%-green security acceptance target is **not achieved**, and deployment should be blocked. No success rate, recovery rate, monetary cost, or crash rate from representative live tasks was measured.

## SARA 3.0 increment — responsive later turns and background conversation (2026-10-16)

### Diagnosis and bounded plan

The real desktop text path is `DesktopChatPanel.tsx` → `/api/chat` → `TextModelRouter` → conversation storage; the separate mobile path is `mobile_server.ts` → the same router. Voice is `src/lib/audio.ts` → `/live` → Gemini Live and its declared tool callbacks. Before this increment, later desktop text turns sent the entire history, the backend repeated that history in more than one context fragment, `/api/chat` rewrote the conversation and the UI followed it with another full-history `/api/conversations` write. Opt-in inferred-memory extraction could hold the response open. Live tool callbacks awaited slow tool calls inline, and an optional late social-policy result could interrupt a newer turn. The existing browser workflow and generic HTTP task runner already background some work; treating every arbitrary tool as newly safe to background would bypass review. The plan was to bound *transport/prompt* context without discarding stored conversations, remove duplicate writes, schedule optional extraction after replies, queue only reviewed long voice actions while keeping verifiable status, and exercise HTTP/Live regressions with fake providers. No major dependency upgrade or UI migration was needed.

### Implementation and boundaries

- `recentChatHistory` caps prior context at 10 recent turns / 8,000 characters (inspecting at most 30 entries and truncating individual long turns); the *current* message is not truncated. Desktop and mobile send/use that context once, and `ContextManager` separates the latest request from already included history while prioritizing real, conversation-scoped task status. This is a prompt and transport bound, **not** deletion or summarization of saved user history.
- `/api/chat` writes the validated user/assistant pair once. The desktop panel caches a confirmed server save without another full-history POST, retains not-yet-saved voice turns through a same-conversation reload, and submits them for validated, deduplicated persistence on the next text turn. Existing custom conversation titles are preserved; default titles can update from the latest text. Accepted text requests are never content-deduplicated: repeating the same message or receiving an identical model answer still saves a distinct turn. The mobile text endpoint also bounds context. Optional, consent-gated inferred-memory extraction now starts *after* reply delivery; it remains unapproved by default and failures do not retroactively fail chat. No claim is made that background extraction works if the process exits before it runs.
- Conversation mutation reads fail closed on malformed or non-list storage, including the legacy snapshot save and delete routes. New writes use a same-directory temporary file and rename; read failures return a generic error and leave the previous data untouched. This is not cross-process transactional storage or a recovery mechanism for an already-corrupt file. A regression deliberately damaged a **temporary test fixture**, not the user's `data/` files.
- Gemini Live acknowledges only reviewed browser work and allowlisted named-app launches as `QUEUED`, deduplicates repeated tool-call IDs, permits at most four active tasks per session, serializes desktop resources and exposes a conversation-scoped status tool. Other direct tool results run off the Live callback instead of holding up the message handler; result-dependent replies can still wait on the tool/provider. Queued is *not* verified completion. A task completes only with a passing verifier check and an explicit verified result; an uncertain outcome pauses for review instead of silently replaying a possible side effect. Native-app launch verification now requires a nonempty matching application identity, not a browser tab title or the empty-string match. The Live social-plan continuation is guarded against later/completed turns. `saraAgentExecute` was not newly exposed in Live, and the separate generic HTTP task runner was not relabeled as verified automation.

### Reproducible checks and limits

- Before/after fake-provider fixture: a later desktop request's repeated history marker went from **2** to **1** occurrence; its captured prompt went from **12,048** to **5,703** characters. For a separate 22-turn local fixture, encoded request history went from **7,988** bytes to **3,638** bytes (10 retained turns). These are deterministic fixture *sizes*, not measured token billing or representative latency. Example fake-provider timings varied by run (e.g. first 64 ms, later 43 ms); no live-provider latency improvement, constant uptime or instant reply is established.
- `tests/api/chat-responsiveness-http.test.ts` checks real HTTP serialization/persistence against a fake provider, pending voice turns, unchanged custom titles, a second chat while browser navigation is held, and fail-closed corrupt-store handling. `tests/api/mobile-chat-responsiveness-http.test.ts` checks the separate mobile route; `tests/chat-context.test.ts`, `tests/chat-background-memory.test.ts`, `tests/desktop-chat-panel.test.ts`, `tests/voice-background-chat.test.ts`, `tests/window-verifier-background.test.ts`, and automation tests cover bounding, asynchronous work, scoped status and verification. The workflow fixture uses a held fake desktop tool, **not** a live browser/desktop installation.
- After the final implementation, `npm run test:chat` **10/10**, `npm run test:voice` **24/24**, `npm run test:agent-core` **54/54**, `npm run test:api` **11/11**, `npm run build` (including lint) **PASS**, `git diff --check` **PASS**. The prior broader regression sweep also passed closed-loop **9/9**, persistence **19/19**, AGI **19/19**, autonomous **4 PASS / 4 SKIP**, Python fake workflow **5/5**, and deterministic agent evaluation **13/13** (local-fixture Wilson 95% interval 0.772–1.000; not a generalization claim). `test:security` remained **24/25** because it detects **1,205** pre-existing tracked generated/private files. That release blocker is not fixed by this latency patch; do not erase user data or ship on the basis of these fixture tests.

**Operating limitation:** Keep the server and voice connection running to process queued work. Check a returned task ID or the existing TASKS interface before claiming completion; a restart can pause unfinished work for explicit review. Provider generation, a necessary tool result, a congested browser/OS, network failure or the mobile device can still delay a turn. Text chat remains one outstanding send per panel; there is no new text streaming, concurrent text-generation engine, global scheduler, or Windows/Android/live-voice performance measurement. Next steps are instrumented p50/p95 end-to-end and per-stage latency on consenting installations, realistic long-task interruptibility tests on each supported platform, and separate remediation of the tracked-data security incident.
