# SARA 6.0 — opt-in account protection (implementation status, 2026-10-16)

**This is an incremental, fail-closed protected mode, not a complete multi-user release.** The existing single-user app remains the default. Activating accounts deliberately disables voice, desktop/Office/browser tools, camera/screen server APIs, standalone mobile APIs, the Python desktop agent, legacy cognitive/admin/task routes, and unscoped automation. Do not enable protected mode if you need those functions today. It is not safe to re-enable them merely by showing UI controls or by assigning a relationship label.

## 1. Actual platform and entry points

- React 19 + Vite 6 + TypeScript 5.8 web UI (`src/main.tsx`, `src/App.tsx`), packaged in Electron (`electron/main.cjs`) and Capacitor 8 Android. An `app.json` file mentions Expo, but there is **no installed Expo or React Native application**. No biometric dependencies were added.
- `server_full.ts` is the built and supported Node/Express backend (`npm run dev`, `npm run build` → `dist/server.cjs`). `mobile_server.ts` is a separate legacy companion backend. `server.ts` is an older standalone entry point and now **refuses to start** against a protected or pending account store. It also blocks runtime HTTP/Live traffic and shuts down if accounts are activated while it is running.
- `desktop_agent/main.py` is a separate Python FastAPI process; `electron/main.cjs` contains native capture handlers. The protected flag and pending-activation marker are checked in these processes independently. Standalone Vite dev/preview and the embedded Vite server deny private runtime paths (`data`, `logs`, `users`, `@fs`, `.env`, `.git`).

```text
UserAccess (React renderer) --same-origin /api + session--> Express protectedApiGate
  -> MultiUserRouter -> MultiUserStore (account/roles/credential/audit JSON)
  -> scoped /chat, /memories, /conversations -> original owner's legacy data
                                          or data/users/<verified ID>/*
  -> all other legacy tool/capture/mobile/voice routes -> DENY in protected mode
```
The trust boundary is the server-verified session; a browser form field, display name, relationship, companion key, image or voice sample cannot create one. The old single-user runtime is preserved only while protection has **not** been enabled.

## 2. Data model, migration, and authorization

- `src/security/multiUserStore.ts`: stable random account IDs (original installation owner is `default-user`), roles, per-account allow/deny capability changes, independently stored descriptive relationships, validated personal preferences, hashed session tokens, one-time invitation/recovery codes, salted scrypt passphrase verifiers, WebAuthn public keys, and account activity metadata. Neither relationships nor voice/face observations authenticate a person. The manager directory exposes active-session counts and last authenticated activity, **not** another person's private preferences or content.
- Default capabilities: owner `chat`, `memory`, `manage_users`, `manage_security_settings`, `view_security_events`; admin/member `chat`, `memory`; restricted **none**; guest `chat` with no saved chat/memory. `manage_users`, `manage_security_settings`, and `view_security_events` are effective only for owner/admin; the latter two require explicit owner grants for admins, and their security actions also require a fresh passkey sign-in. The original owner can use their local secret instead. `chat`/`memory` may be individually granted to restricted accounts; guests can only chat temporarily. **No capability grants cross-account private content or biometric enrollment.** Role or account permission changes revoke affected sessions.
- `src/security/multiUserHttp.ts`: authenticated same-origin account routes and a **positive allowlist** for protected `/api` routes. Chat, approved memories, conversations, own profile, and account controls are scoped to the verified session. Client `userId`, device bearer, speech transcript, face, and descriptive relation cannot change that scope. All unported routes fail closed even for owner. The text provider is installation-wide: configure it **before** activation or use a separately reviewed local server configuration procedure; `/api/config/apikey` is deliberately unavailable after activation.
- `src/security/userData.ts`: invited members' memory and conversation JSON lives under `data/users/<opaque-id>/`; original desktop owner records remain in their legacy files/SQLite. Guest chat is not persisted. Only an authenticated original owner can read their legacy data. New JSON writes are atomic; account-store writes have an inter-process `wx` lock. Protected approved-memory read/modify/write operations are serialized within the Node process. Protected chat bounds text/metadata and refuses client-supplied voice turns; it cannot invoke legacy tools. This is **not** full multi-process transactional isolation, encrypted storage, or a per-user storage/cost quota.
- Bootstrap is **explicit and local**, requires a configured 32+ character `SARA_ADMIN_TOKEN`, and copies important legacy data files into a restricted `data/security/backup-*` directory **before** creating the store. `server_paths.ts` loads local `.env` **before** resolving `SARA_DATA_DIR` or instantiating the protection guard; the startup supervisor and Electron use the same configured directory/flag for their children/native capture guard. A disposable-cwd process test verifies an `.env`-only required flag locks legacy APIs before setup. It does not import legacy profile labels as verified people or enroll biometrics. A `multiuser.pending` marker locks legacy paths after an interrupted setup; a damaged/missing required account store also remains locked. Do not manually delete this marker to reopen an installation. Back up and review the store and directory permissions offline before recovery.
- Older experimental account stores with a `child` role **are not automatically migrated** to `restricted`: this transition could silently change grants or strand an account without another credential. Back up such a store and plan a reviewed offline migration; the current validator locks an unknown role rather than guessing. Version-1 stores without an idle-lock setting use 15 minutes; those without preferences use `en` and both opt-in toggles off. Pre-existing owner role arrays gain effective owner security controls without rewriting the file. Invalid/corrupt preferences lock protected APIs for review rather than silently resetting another person's choices.

## 3. Enrollment and sign-in (what they actually prove)

- New accounts receive a one-time invitation. The recipient must enter their own code; a manager cannot replace an **accepted** invitation or issue a recovery code for somebody with existing private history. The signed-in person can issue/replace their own one-time recovery code. Consuming an invitation/recovery code and issuing its session now happen in one atomic account-store update, so an interrupted write cannot consume the code without issuing a session. Recovery invalidates old passkeys, passphrase, and sessions. Keep codes private and offline.
- Where browser and OS support it, the signed-in holder can explicitly consent to register their **own** platform WebAuthn passkey (up to five). The server verifies origin, RP ID, challenge, signature and required user verification via the already installed SimpleWebAuthn packages. Passkey sign-in binds a specific enrolled credential to its account ID. A freshly verified holder can revoke their own enrollment (this also revokes all their sessions); revoking the last one requires an alternative personal credential/recovery code unless it is the original owner with a local owner secret. It establishes possession of a registered signing key and verifies the protocol's user-verification flag, **not** independently attested hardware/device verification, face liveness, named-person recognition, proof of consent from the human behind a checkbox, or a tested Windows Hello/Android biometric flow. Attestation is set to `none`; the UI requests a platform authenticator, but a direct API client with a valid personal invitation/session can present a software-generated key. No server-side claim is made about the authenticator's physical type or the identity of its operator. Protocol tests use a **software-created P-256 credential** to verify signature, challenge, origin, RP ID, UV flag, counter, replay and revocation checks; this is not an OS passkey or a real biometric acceptance test. Registration rechecks the active session *after* the asynchronous cryptographic verification, before writing a credential.
- A user can instead set a unique 16–256 character personal passphrase (salted scrypt verifier only); changing it revokes other sessions. The original owner can authenticate with the server's local admin secret. Strongly authenticated owner/passkey re-authentication within two minutes is required for permission changes. Own passphrase/recovery/session actions require a recently authenticated session. A separate cross-account recovery/reset service is **not** implemented. Guests cannot save a passkey, passphrase, recovery code, language choice or permanent profile update; a former member demoted to guest cannot renew access through previously enrolled credentials.
- Sessions have an 8-hour absolute lifetime (30 minutes for guests) and a configurable **5–60 minute idle lock**, default 15, set by a freshly authenticated owner or an explicitly authorized, passkey-verified admin. Server-side `/api/users/me` polling and passive account-settings/session reads do not renew activity. Authenticated interactive actions do. Sign-out clears the local UI immediately and attempts server revocation. Switching accounts clears old browser conversation caches, browser-wide settings/experimental voice similarity samples and legacy admin UI tokens; other tabs receive a local storage event to lock, with a 30-second server-check fallback. Browser sessionStorage, not an HttpOnly cookie, holds the token; same-origin script injection, hostile browser extensions, developer tools or local malware can read it. Users sharing one OS/browser profile should not assume cryptographic isolation.

## 4. UI and data controls

`src/components/UserAccess.tsx` adds responsive sign-in/setup, a people directory (pending invitation, active-session count, last authenticated activity, owner-only revocation), role matrix and individual grants/denies, separately editable relationship labels (presets or custom, owner-only create/remove), profile/preferences, passkeys, passphrases, recovery, own session controls, configurable inactivity, own activity, restricted installation security activity, and private-data export. A teacher/family label never changes permissions. Owner can view relationship metadata to manage it; other users see only labels involving themselves. Only the account holder can see/edit their personal settings (`en`, `hi`, `mr`, `gu`, `bn`, `ta`, `te`, `kn`, `ml`, `pa`; greeting and future proactive-conversation opt-in). Chat prompts receive the account's selected language, and an optional greeting shows **only the chosen display name in that account's private UI**. The model's language compliance is unverified; proactive background/voice runtime is **still disabled in protected mode**, regardless of stored opt-in. These choices are never inferred from appearance, speech or relations.

Non-owner users use a dedicated private chat/memory workspace; its conversations can be selected/deleted, and approved memories can be created/corrected/deleted. Owner keeps the legacy chat layout under the protected API boundary; other unscoped controls cannot call their old server routes. Guests have temporary chat with no persisted memory or conversation, though invitation/usage metadata remains on disk for local accountability; do not promise guest records or historical backups are erased. The setup page warns that *browser-only* legacy settings and voice samples are removed on first protected sign-in, while on-disk legacy data is backed up.

`/api/users/security/activity` shows the owner or explicitly permitted, freshly passkey-verified admin at most 100 recent account/security **metadata** events; ordinary members can view only their own activity, while restricted/guest roles have no activity screen. The owner may terminate a non-owner's active sessions without reading that account's content. Account/role/relationship changes and self-data exports are logged, but not every chat, memory, tool denial or data access is logged; the audit file is not tamper-evident and has no automatic retention limit.

A **fresh** authenticated `/api/users/me/export` contains only the caller's profile, accessible memories/conversations, and relationship labels involving that caller. It excludes session hashes, secrets, passkey material and other users' data; the export event is recorded in the account audit log. **Account-wide deletion, secure erasure of backups, cross-device deletion, retention policy, tamper-evident audit, account-bound encryption and a complete data inventory are not implemented.** A deleted live conversation/memory may still exist in previously made backups, browser downloads, earlier external exports, or historical Git commits. Do not promise irreversible deletion.

## 5. Protected services and known boundaries

- Node: `/api` allowlist, chat tool execution disabled, background wake/task/webhook services stopped/not started, authenticated conversation/memory checks, in-flight chat response discarded on session expiry/revocation, same-origin Host/Origin checks, private static-file denial and negative path tests. `src/lib/userSession.ts` does not attach a token to non-API URLs or follow redirects. The legacy `server.ts` manual entry point is disabled when protection is active.
- Python desktop agent: every route other than `/health` returns 403 in protected mode; its dependency-free guard also reads an `.env`-only required flag and custom data path when launched independently from the same application root (tested without FastAPI). Electron: native screen-capture handlers reject protected mode and check the actual backend directory, an older user-data directory and the default project directory (negative test is a pure helper; Electron itself was not run). Separate mobile server: all `/api` routes reject, including attempts that supply desktop session headers. Live voice upgrade is refused in the primary backend; bootstrap ends pre-existing unscoped sockets.
- **Operational limit:** other previously running processes or already-dispatched desktop actions may not be cancellable at the exact moment of activation; effects remain uncertain. Multiple `server_full.ts` processes sharing the same data directory are unsupported. Independently launched Python/legacy processes **must** receive the same `SARA_DATA_DIR` and `SARA_MULTIUSER_REQUIRED` environment or run from the same application root with its `.env`; otherwise they may not see an alternate install's marker. Never leave an older manually launched agent running with a different datastore when activating protection. Require human review before integrating identity/scope in each tool, Python execution, screen/camera capture, Android companion, or Live voice route. Identity is **never** inferred from voice similarity, a photo, device proximity, or a transcript.

| Component | Implemented protected-mode behavior | What remains to validate |
|---|---|---|
| Web/Electron renderer | Server-verified gated accounts, mobile-responsive management, personal chat/preferences, native capture blocked | Manual browser interaction, Electron packaging and real OS authenticator |

Primary files for this phase: `src/security/{multiUserStore,multiUserHttp,userData,privateStaticPaths}.ts`, `src/lib/userSession.ts`, `src/components/UserAccess.tsx`, `server_full.ts`, `server.ts`, `server_state.ts`, `server_paths.ts`, `startup/startupManager.ts`, `mobile_server.ts`, `desktop_agent/{identity_guard,main}.py`, `electron/{main,nativeGuard}.cjs`, `vite.config.ts`, `.env.example`, `package.json`, `README.md`, this guide, and `tests/security/{multi-user-store,multi-user-preferences,multi-user-webauthn,multi-user-config,private-static-paths,user-session,legacy-server-guard}.test.ts` + `tests/api/multi-user-http.test.ts`. Pre-existing Office/screen/camera/agent files modified in earlier work on this branch are **separate from** the account protection boundary; they remain disabled in protected mode.

No destructive schema conversion is applied. Activation copies selected legacy files, creates `security/multiuser.json` (version 1), `security/relationships.json` as labels are added, and an append-only local audit JSONL; invited members' private JSON stores are created on first save. An explicit pending marker prevents reopening legacy access after interruption. `SARA_DATA_DIR` should point to a private, backed-up installation directory. If a migration or store validation fails, stop services, preserve files and review offline; no automatic downgrade/rollback is safe.

## 7. How to run safely

1. Keep an offline, private backup of your data directory. In an ignored local `.env` or secure process environment, configure a supported text provider (`GEMINI_API_KEY` or `SARA_TEXT_PROVIDER=openai-compatible` with model/base URL/key as applicable), a random `SARA_ADMIN_TOKEN` of at least 32 characters, and optionally a dedicated private `SARA_DATA_DIR`. Do not assume a model name is available without provider verification. Never commit a secret. For a **new disposable installation**, use a dedicated `SARA_DATA_DIR`; never point tests or sample scripts at an active user's directory. Existing `SARA_REMOTE_ACCESS_TOKEN`, TLS, Host/Origin allowlists still apply for non-loopback access; a remote access token is not a named person or a substitute for account sign-in.
2. Start the **supported** backend with `npm run dev` (or `npm run build && npm start`). Browse the local UI, select **Secure users**, read the migration warning, and opt in with the locally configured owner secret. Alternatively set `SARA_MULTIUSER_REQUIRED=true` **before starting**, which locks old endpoints until local owner bootstrap. Activation cannot be undone in the UI. For passkeys use a browser secure context (HTTPS, or browser-supported localhost) and set `SARA_WEBAUTHN_RP_ID` only to a verified DNS host matching the browser origin. A passkey for one origin/RP cannot be used on an unrelated domain.
3. As owner, invite a member. Share **both** the generated account ID and one-time invitation code privately; each person accepts them in the UI and chooses their own passkey where supported or a fallback passphrase. They should generate and save their own recovery code. Review capabilities and relationship labels separately; optional admin security capabilities require their own fresh passkey verification. Lock/switch between users and confirm private histories are distinct.
4. If recovery or migration fails, **stop services, preserve the store, backups and marker, and review offline**. Do not delete `multiuser.json` or `multiuser.pending` to bypass the lock. Use owner secret locally to reauthenticate; a user's recovery requires that user's previously issued one-time code. There is no backdoor to an active user's private data.

Reproducible **Linux source-check** commands below use `--ignore-scripts` to avoid running optional native install hooks here; real Electron/native packaging on a supported machine may require a normal `npm ci` and the platform build prerequisites. No Expo packages or new biometric dependency were added.
