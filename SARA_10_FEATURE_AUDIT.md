**Audit date:** 2026-10-16<br>
**Repository:** `Pandhare-amol/Sara`<br>
**Audit basis:** Source/configuration inspection of the active frontend, backend, task/memory services, Windows-agent code, tests, and build/deployment scripts. A source path or UI control is not treated as proof of runtime behavior. Existing uncommitted work was preserved.

## Architecture actually present

- The active renderer entry is `src/main.tsx` → `src/App.tsx`. The desktop product uses Electron, Vite, and React.
- Android is configured through Capacitor (`@capacitor/*`, `capacitor.config.*`, and `android/`). `app.json`/`eas.json` exist, but the package does not configure an Expo runtime or `expo-updates`; no checked-in iOS project was found. Do not claim a supported Expo runtime without separately establishing one.
- `server_full.ts` is the primary Node backend candidate; it calls the separate Python desktop agent. Agent transport authentication was added in the preceding increment.
- Root-level `App.tsx` and `TaskManagerPanel.tsx` are not the active `src/` renderer paths. The active `src/App.tsx` does not mount the older task-manager panel.

## Prioritized implementation plan

1. **P0 — Authorization and approval boundary:** The initial slice removes model/request consent booleans as authority on the central tool path, adds argument-bound, expiring, single-use pending approvals, gates generic high-risk calls plus direct WhatsApp/voice requests, and avoids duplicating new approval arguments into unscoped task metadata or general tool-call history; pending retries require a fresh request/approval. Next bind approvals to a real authenticated principal/session and record the approver; inventory and close remaining direct high-impact routes (power/process actions, publishing, workflow apply, and retry), then test the boundary end to end.
2. **P1 — Identity and data isolation:** Establish a real authenticated principal/session and role boundary. Scope profile, conversation, task, and private-memory reads/writes/deletes to that principal; review tracked runtime data and secret storage before release.
3. **P2 — Reliable task, workflow, and memory behavior:** Consolidate persistent task lifecycle, checkpoint/cancellation semantics, bounded retry/recovery and idempotency; implement verified reusable workflows; add memory expiry, contradiction resolution, provenance-aware retrieval, and user export/delete.
4. **P3 — Voice and offline behavior:** Validate interruption/privacy and microphone controls; define explicit local/offline capability reporting; only then integrate an optional local model and durable, deduplicated offline queue. Keep proactive behavior configurable and visible.
5. **P4 — Release, testing, and operations:** Correct platform build paths, add route-level and platform tests, performance/concurrency checks, trusted signature verification, staged rollout, backup/rollback, health checks, and privacy-preserving measurable telemetry.

### First incremental slice

The first P0 implementation increment now ignores top-level consent fields embedded in tool arguments, removes the power-token-as-consent shortcut, strips consent-shaped downstream fields, classifies additional high-risk tools, and adds regression coverage. Generic high-risk desktop/voice WebSocket calls and direct WhatsApp/voice HTTP requests create pending approvals; pending approvals bind the exact action and arguments with a random process-local HMAC key and are consumed before dispatch. Newly created approval tasks no longer duplicate private arguments into metadata returned by `/api/tasks` or general tool-call history; the latter records only an approval marker and argument keys. The exact preview is served by the admin-authenticated approval list, and retries require a fresh request/approval. The key is not persisted, so restart invalidates pending approvals. This does not complete P0: no origin principal/session is bound, the active approver is not recorded as a durable identity, and other direct high-impact routes remain to audit.

**Sequencing note:** The feature inventory and prioritized plan were documented before implementation began. During implementation, inspection of `src/App.tsx` and `src/lib/audio.ts` established that the existing confirmation panel is mounted and automatically opened on `confirmation_required`; the original audit wording did not reflect that. Source and test changes continued before this audit correction. After correcting the audit, full-diff review exposed that pending action arguments were duplicated into task metadata and tool-call history; this increment now keeps the exact preview in the approval store/list, records only an approval marker and argument keys in general tool history, and requires a fresh approval for retries. The ordering deviation and correction are recorded here. Review the remainder of the full diff before beginning the next implementation slice.

### Task-reliability follow-up: completion requires structured verification (2026-10-16)

AutomationOrchestrator now marks work completed, and allows post-success cleanup, only when the result has a consistent success/verified state plus a non-empty set of passing verification checks. It accepts the repository's authoritative task-result shape (verification attempted and passed) and unified execution-result shape (verification status `verified`). Naked `verified` flags, missing/failed checks, or contradictory top-level state pause for review. This narrows false-success cases on the async automation path; it does not establish verification on every task entry path or durable cross-session idempotency.

### Identity-profile API hardening slice (2026-10-16)

The profile-management list/read/write endpoints now require the existing admin authentication boundary and return `Cache-Control: no-store`. The profile store uses `SARA_DATA_DIR`; when it finds a valid, bounded legacy JSON store and the configured destination is absent, it copies the file into the configured location, retains the original, and applies restrictive file permissions where supported. This protects profile administration as a privileged operation; it does **not** create a general user session or make profile IDs trustworthy. The chat endpoint still accepts caller-supplied `userId`, and memory/task ownership is not yet scoped to an authenticated principal.
